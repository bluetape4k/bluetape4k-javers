# Issue #244 — Javers 0.2 매뉴얼 설계

## 배경

`bluetape4k-javers` 0.2.1은 JaVers의 객체 변경 추적 모델을 Kotlin 중심 API, Exposed JDBC, Redis, Kafka, DDD/CQRS 흐름과 연결한다. README와 모듈별 문서는 개별 기능을 소개하지만, 독자가 저장 방식과 이벤트 흐름을 선택하고 학습 순서를 정하며 운영상 실패 지점을 진단할 수 있는 버전 고정 매뉴얼은 없다.

이 매뉴얼은 README를 합쳐 놓은 문서가 아니라 Javers 0.2 사용 계약의 기준 문서다. 작성 원본은 이 저장소의 `docs/manual/`에 두고, 웹사이트는 검증된 snapshot만 게시한다.

## 릴리스 경계

- 공개 minor 버전: `0.2`
- 안정 릴리스: `0.2.1`
- 릴리스 커밋: `bffe19439ca891fa5301a76421bdef7ba75252a0`
- 작성 기준: 매뉴얼 PR이 병합된 `develop` 커밋
- 소비자 버전 기준: `bluetape4k-dependencies` 한 개
- 릴리스 inventory: 라이브러리 5개, BOM 1개, 예제 1개, 벤치마크 결과 1개

0.2.1 이후 `develop`에 추가된 `javers-spring-boot4-autoconfigure`, `examples/javers-ktor`, `examples/javers-spring-boot4`, `benchmark/javers-exposed-benchmark`는 0.2 매뉴얼의 현재 기능으로 설명하지 않는다. 필요한 곳에서는 다음 minor 버전에서 다룰 범위라는 경계만 밝힌다.

## 검토한 접근

### 1. README 조합형

루트와 모듈 README를 순서대로 연결하거나 짧게 재구성한다. 빠르지만 Exposed·Redis·Kafka의 역할 차이, 감사 commit과 도메인 이벤트의 순서, 장애 진단, 학습 경로가 흩어진다. README가 사실상의 원본이 되므로 채택하지 않는다.

### 2. 저장소 소유 매뉴얼형 — 채택

`docs/manual/`에 영문·한글 원문, manifest, 생성·검증 도구, 다이어그램 원본을 둔다. 웹사이트는 릴리스 provenance와 작성 커밋을 기록한 snapshot을 생성한다. 문서량은 늘지만 버전 경계, 링크 검증, 양 언어 동등성, 향후 블로그와 다른 저장소 매뉴얼의 교차 링크를 일관되게 관리할 수 있다.

### 3. 웹사이트 직접 작성형

사이트 저장소에서 설명을 작성한다. 배포 구조는 단순하지만 코드와 문서가 분리되어 API 변경과 릴리스 검증이 늦어진다. source of truth 원칙에 맞지 않아 채택하지 않는다.

## 정보 구조

### 시작과 선택

1. 개요와 저장소 지도
2. `bluetape4k-dependencies` 기반 설치
3. 10분 빠른 시작
4. 역할별 학습 경로
5. JaVers 기본 개념과 bluetape4k 확장 경계

### 핵심 모델과 API

- JaVers commit, snapshot, change, shadow를 읽는 법
- codec과 Kotlin 확장 함수
- `CdoSnapshotRepository` 계열의 책임
- cache-backed·composite repository 선택 기준
- 감사 commit의 author, properties, commit metadata
- 오류, 직렬화, 취소, 일관성 경계

### 저장 방식 선택

- Exposed: 관계형 DB에 snapshot과 commit metadata를 저장하는 영속 계층
- Redis: Lettuce·Redisson 기반의 빠른 snapshot 저장과 조회
- Kafka: snapshot/event stream을 전달하고 projection을 연결하는 경로
- 각 방식의 source of truth 여부, 내구성, 순서 보장, 재처리, 장애 복구 차이
- Exposed와 Redis를 조합하는 composite/cache 흐름과 중복·실패 처리

### DDD와 CQRS

- aggregate 변경과 JaVers commit의 관계
- 도메인 저장, 감사 commit, 이벤트 발행 순서
- `examples/javers-exposed-ddd`의 command와 query 흐름
- Kafka 이벤트와 Redis projection의 역할
- 예제에서 학습할 부분과 운영 코드로 그대로 옮기면 안 되는 경계

### 운영과 증거

- schema 준비와 migration 책임
- commit metadata index와 조회 패턴
- Redis/Kafka 연결 실패와 재시도 경계
- 관측해야 할 저장 지연, commit 실패, consumer lag, projection 불일치
- 0.2.1에 포함된 Envers 비교 결과를 읽는 법과 벤치마크 한계
- Testcontainers 기반 검증 전략

### 모듈과 학습 경로

- `javers-core`, `javers-ddd`, `javers-exposed`, `javers-persistence-redis`, `javers-persistence-kafka`마다 좌표, 제공 기능, 핵심 API, 빠른 시작, 선택 기준, 실패 유형, 운영, 테스트, 관련 가이드, 제외 범위를 설명한다.
- `bluetape4k-javers-bom`은 소비자가 직접 버전을 맞추는 방법보다 `bluetape4k-dependencies`를 우선하는 설치 경계를 설명한다.
- `examples/javers-exposed-ddd`는 해결 문제, 실행 방법, 관찰 결과, 코드 읽는 순서, 확장 과제, 운영 전환 시 보완점을 설명한다.
- 벤치마크 결과는 라이브러리처럼 소개하지 않고 의사결정 증거 페이지로 둔다.

## 교차 저장소 연결

- `bluetape4k-exposed`: 애플리케이션 repository와 JaVers CDO snapshot persistence의 책임 차이
- `bluetape4k-projects`: DDD, Redis, Kafka, cache, Testcontainers의 기반 기능
- `bluetape4k-dependencies`: 소비자가 알아야 할 단일 버전 진입점
- 향후 Javers 0.3 매뉴얼: Ktor, Spring Boot 4, 전용 벤치마크 모듈로 이어지는 발전 경로

교차 링크는 현재 공개된 상대 매뉴얼 route가 있을 때 직접 연결하고, 아직 공개되지 않은 문서는 저장소 source link로 연결한다. 링크 대상이 생기면 manifest 검증만으로 교체할 수 있게 route metadata를 분리한다.

## 문서 소스 구조

```text
docs/manual/
├── manifest.yaml
├── generated/manifest.json
├── en/
│   ├── index.md
│   ├── getting-started.md
│   ├── architecture/
│   ├── persistence/
│   ├── guides/
│   ├── operations/
│   ├── benchmarks/
│   ├── modules/
│   └── examples/
├── ko/                    # 영문과 동일한 route 집합
└── assets/                # editable SVG + canonical 2x PNG
```

manifest는 release ref/commit, 프로젝트 inventory, 언어별 route, 자산, source path를 한곳에서 관리한다. 생성기는 반복되는 frontmatter와 inventory 검증만 담당하며, 선택 기준과 실패 계약은 사람이 검토 가능한 Markdown 원문으로 유지한다.

## 한국어 품질

한글 문서는 영문 문장 순서를 그대로 옮기지 않는다. API 이름과 표준 기술 용어는 보존하되, 독자가 선택하고 실행하고 진단하는 흐름으로 문장을 다시 쓴다. 각 페이지는 독자의 문제, 가장 작은 실행 예제, 결과 해석, 선택 기준과 주의점 순으로 구성한다. 번역체, 기능 나열, 근거 없는 홍보 문구를 남기지 않는다.

## 검증 계약

- 태그 `0.2.1`이 지정 커밋으로 해석되는지 확인한다.
- release tree의 7개 Gradle project와 벤치마크 결과 1개를 inventory로 고정한다.
- manifest와 실제 영문·한글 route가 정확히 일치해야 한다.
- 모든 source link와 내부 link가 0.2.1 경계에서 존재해야 한다.
- 생성기·manifest·release contract 검증을 실행한다.
- 다섯 diagram pair의 XML, 크기, 접근성, marker, connector geometry를 검사한다.
- 모든 PNG를 마지막 좌표 변경 후 원본 크기로 눈 검수한다.
- `git diff --check`와 문서 범위의 가벼운 검증만 실행한다. 프로덕션 코드가 바뀌지 않으므로 전체 Testcontainers 테스트와 전체 CI는 완료 조건이 아니다.
- 병합 후 사이트 snapshot 테스트, Astro build, 공개 route와 자산 hash를 검증한다.

## 작업 분리

- 공통 계약, manifest, 개요, 설치, 핵심 개념
- 다섯 library module과 BOM 페이지
- DDD/CQRS 예제, 운영, 벤치마크, 교차 저장소 가이드
- 다이어그램과 최종 통합·검증

각 영역은 파일 소유권을 분리해 병렬 작성할 수 있다. 공통 manifest와 index, 검증 도구, 릴리스 경계, 양 언어 자연스러움, 최종 자산 감사를 통합 담당자가 책임진다.

## 완료 조건

매뉴얼은 README보다 상세해야 하며, API 사용법뿐 아니라 저장 방식의 역할, 선택 기준, 실패 계약, 운영, 테스트, 학습 순서를 제공해야 한다. 0.2.1에 없는 기능을 현재 계약처럼 설명하지 않고, 영문과 한글 route가 완전히 대응하며, 다이어그램과 공개 웹 snapshot까지 검증돼야 완료다.
